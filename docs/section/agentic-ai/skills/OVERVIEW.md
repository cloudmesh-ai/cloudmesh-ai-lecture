# Agentic AI: The Skills Library

!!! info "Learning Objectives"
    By the end of this module, students will be able to:
    - Define a "Skill" (Tool) in the context of Agentic AI.
    - Write precise JSON schemas for function calling that minimize LLM hallucinations.
    - Implement a set of interdependent skills to create a closed-loop autonomous system.
    - Apply the "Principle of Least Privilege" to agent toolsets.

## Overview

In a standard LLM interaction, the model is a "brain in a vat"—it can reason but cannot act. To transform an LLM into an Agent, we must provide it with **Skills**. In technical terms, a skill is a tool: a discrete piece of executable code wrapped in a metadata description that tells the LLM *when* and *how* to use it.

For the AI-Guided Code Optimization system, a single "do everything" tool is too prone to error. Instead, we decompose the problem into a **Skills Library**. By breaking the process into discovery, optimization, and validation, we allow the agent to reason about each step independently, observe the result, and iterate.

## The Anatomy of a Skill

A skill consists of two parts: the **Implementation** (the Python/Bash code that does the work) and the **Definition** (the JSON schema the LLM reads).

### The Definition (The "Interface")

The definition is the most critical part of agent design. If the description is vague, the LLM will call the tool with incorrect arguments.

Example of a high-quality skill definition:

```json
{
  "name": "execute_benchmark",
  "description": "Runs a compiled binary and returns the precise execution time in milliseconds. Use this ONLY after a binary has been successfully compiled.",
  "parameters": {
    "type": "object",
    "properties": {
      "binary_path": {
        "type": "string",
        "description": "The absolute path to the compiled executable file."
      },
      "input_file": {
        "type": "string",
        "description": "Path to the dataset file used for the benchmark."
      }
    },
    "required": ["binary_path", "input_file"]
  }
}
```

Why this matters: By specifying "Use this ONLY after a binary has been successfully compiled," we provide a behavioral guardrail that guides the agent's reasoning process (the "Thought" in ReAct).

## Core Skills for Code Optimization

To build the autonomous optimization loop, the agent requires the following specialized skills.

### 1. The Discovery Skill (`analyze_code`)

This skill allows the agent to scan a source file and identify "hotspots"—sections of code (like nested loops) that are prime candidates for GPU acceleration.

**Why this matters**: Without a discovery skill, the agent would have to read the entire codebase into its context window, which is expensive and often exceeds token limits.

**Implementation Detail**: This skill typically wraps a combination of static analysis (using Python's `ast` module) and dynamic analysis (using `perf` or `gprof`).

### 2. The Optimization Skill (`propose_rewrite`)

This skill takes a identified code kernel and a target architecture (e.g., NVIDIA CUDA or AMD ROCm) and returns a proposed GPU-friendly implementation.

**Why this matters**: This is the creative core of the agent. By isolating this as a skill, we can version the prompts used for rewriting without changing the rest of the agent's logic.

**Implementation Detail**: This is often a "meta-tool" that triggers a specialized LLM prompt designed specifically for kernel optimization.

### 3. The Validation Skill (`run_and_verify`)

This skill compiles the proposed code, executes it against a benchmark, and returns the performance delta.

**Why this matters**: This provides the "Observation" in the agentic loop. The agent cannot "know" if the code is faster; it must *observe* the clock.

**Implementation Detail**: This skill must run in a highly restricted sandbox (e.g., a Docker container) because it executes arbitrary code generated by an AI.

### 4. The Resource Skill (`manage_gpu`)

This skill handles the provisioning of GPU resources, checking availability, and cleaning up after a benchmark run.

**Why this matters**: In a cloud environment, GPU hours are expensive. An agent that forgets to release a GPU after a failed run can quickly exhaust a project's budget.

## Implementation Strategy: The Skill Chain

These skills are not used in isolation; they form a **chain of dependency**.

1. `analyze_code` $\rightarrow$ Returns a list of kernels.
2. `propose_rewrite` $\rightarrow$ Takes a kernel $\rightarrow$ Returns CUDA code.
3. `run_and_verify` $\rightarrow$ Takes CUDA code $\rightarrow$ Returns "Slower by 20%".
4. **Reasoning Step**: The agent observes the failure $\rightarrow$ decides to call `propose_rewrite` again with a different strategy.

:::warning
**The Tool-Call Loop**
Avoid creating "Circular Skills" where Tool A calls Tool B, which calls Tool A. This leads to infinite loops that can crash the agent and consume thousands of tokens in seconds. Always ensure the agent's main loop (the orchestrator) is the one managing the sequence.
:::

## Self-Evaluation

??? note "Why is the description field in a tool definition just as important as the parameters?"
    Because the LLM uses the description to decide *if* the tool should be called. A poor description leads to the agent calling the wrong tool or ignoring a useful one.

??? note "What happens if an agent calls a tool with an argument that doesn't match the JSON schema?"
    The system should return a validation error to the agent. A well-designed agentic loop will then take that error as an "Observation," reason about the mistake, and attempt to call the tool again with the correct arguments.

??? note "How does the 'Discovery Skill' prevent context window overflow?"
    By extracting only the relevant "hotspots" from a large codebase and passing only those small snippets to the LLM, rather than the entire file.

??? note "In a multi-agent system, should all agents have access to all skills?"
    No. Following the Principle of Least Privilege, agents should only have the skills necessary for their role (e.g., the Reviewer Agent should have `analyze_code` but not `manage_gpu`).

??? note "What is the risk of allowing an agent to write its own tool definitions?"
    This creates a recursive security risk where the agent could define a tool that grants it unauthorized access to the underlying host system or bypasses existing guardrails.
